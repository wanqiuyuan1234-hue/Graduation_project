# 第一部分：PyCharm Community 详细配置

## 1.1 安装 Python（必须先装）

1. 打开 Python 官网：<https://www.python.org/downloads/>
2. 下载 **Python 3.10.x** 或 **3.11.x** 的 Windows 安装包（推荐 3.11，生态兼容性最好）。
3. 运行安装程序，**务必勾选底部 "Add Python to PATH"**，然后点 "Install Now"。
4. 安装完成后，打开 PowerShell 验证：

```powershell
python --version
# 应输出类似：Python 3.11.9
```

> ⚠️ 如果 `python --version` 报错或没反应，说明 PATH 没配好，重新运行安装包并勾选 "Add Python to PATH"。

## 1.2 下载并安装 PyCharm Community（中文界面说明）

1. 打开官网：<https://www.jetbrains.com/pycharm/download/>
2. 选择 **Community Edition（社区版，免费）** 下载（Windows 64 位）。
3. 运行安装程序，一路"下一步"安装。安装时可勾选（中文版安装引导里的选项目）：
   - **"Add 'Open Folder as Project'"** 或 **"添加'作为项目打开文件夹'"**：方便以后右键文件夹直接打开（推荐勾选）
   - **"关联 .py 文件"** 或 **"Associate .py files"**：让 `.py` 文件默认用 PyCharm 打开（推荐勾选）

> 提示：你是中文版 PyCharm。如果你装完发现是英文界面，可以切换成中文：
> 菜单 **文件(File) → 设置(Settings) → 插件(Plugins)**，在"市场(Marketplace)"里搜索 **Chinese (Simplified) Language Pack / 中文语言包**，安装后重启 PyCharm 即可变中文。
>
> 如果已经是中文版，跳过这一步。

> 提示：你有 IDEA 的使用经验，PyCharm 和 IDEA 同属 JetBrains，中文界面的菜单命名、快捷键、Git 面板几乎一致，可无缝上手。

## 1.3 新建项目（含解释器类型、环境、Git 仓库的完整选择）

这是最容易点错的环节，请严格按照下面顺序操作。

**第 1 步：打开新建项目窗口**

启动 PyCharm，在欢迎界面点 **"新建项目（New Project）"**；
如果已经进入编辑器，则点顶部菜单 **文件(File) → 新建项目(New Project)**。

**第 2 步：填写"位置"**

在 **位置(Location)** 输入框里，填入或浏览选择：

```
C:\Users\w\Desktop\保研资料\code-rag
```

> ⚠️ 项目名建议就叫 `code-rag`，路径里不要有中文和空格，避免后续工具（tree-sitter、uvicorn）出现兼容问题。

**第 3 步：选择"解释器类型（Interpreter type）"**

新版本的中文界面里有一个 **解释器类型** 下拉框，请选择 **Python**（不要选 Conda、Poetry 等其他类型，除非你确定自己在用它们）。

**第 4 步：选择"环境（Environment）"**

在 **环境** 这一栏，会有两个单选选项：

| 选项                                  | 中文名         | 该不该选     |
| ------------------------------------- | -------------- | ------------ |
| **New environment**                   | 新建环境       | ✅ **选这个** |
| **Previously configured interpreter** | 选择现有解释器 | ❌ 不选       |

选"新建环境（New environment）"，PyCharm 会为你的项目单独创建一个隔离的虚拟环境。

**第 5 步：选择"新建环境"的具体类型**

在"新建环境"下面，还有一个 **新建环境使用(New environment using)** 或 **类型(Type)** 的下拉框，选 **Virtualenv**（中文叫"虚拟环境"，有的版本叫 "Venv"）。其余选项（Conda、Poetry、Pipenv）都不选。

> 为什么用虚拟环境：每个项目独立隔离依赖，避免不同项目之间的包版本冲突。这是 Python 开发的标配做法。

**第 6 步：选择"基础解释器（Base interpreter）"**

在 **基础解释器(Base interpreter)** 下拉框里，选择你在 1.1 节安装的那个 **Python 3.11**（通常会自动识别到，显示类似 `Python 3.11 (python.exe)`）。

> ⚠️ 如果这里看不到 Python 3.11，说明 1.1 节没装好或没勾选"Add Python to PATH"，回到 1.1 节重新确认安装。

**第 7 步：关于"创建 Git 仓库"的勾选**

在新建项目窗口里，如果出现类似 **"创建 Git 仓库（Create a Git repository）"** 的复选框：

- ✅ **建议勾选**。本项目后续要用 GitHub 托管代码、做版本管理，现在勾上会在项目建好时自动初始化一个本地 Git 仓库，省得后面再手动初始化。
- 如果没勾上也不要紧，事后随时可以用菜单 **VCS → 启用版本控制(Enable Version Control Integration) → Git** 补上。

**第 8 步：其他勾选项**

- **"创建 main.py 欢迎脚本（Create a main.py welcome script）"**：可勾可不勾（勾了会生成一个示例 main.py，之后我们要自己写，可以不管它）。

**第 9 步：点击"创建（Create）"**

点 **创建(Create)**，PyCharm 会自动生成项目并在项目根目录创建一个 `venv` 文件夹（这就是你的虚拟环境）。等待右下角进度条走完即可。

> ✅ 完成后核对：项目左侧"项目(Project)"面板里应能看到 `code-rag` 目录，且里面有一个 `venv` 文件夹，说明虚拟环境创建成功。

## 1.4 确认解释器与终端

1. 右下角应显示 `Python 3.11 (code-rag)`，表示虚拟环境已生效。
2. 打开 PyCharm 内置终端（底部 **Terminal** 标签），应看到命令提示符前有 `(venv)` 字样，例如：

```
(venv) PS C:\Users\w\Desktop\保研资料\code-rag>
```

3. 如果终端没显示 `(venv)`，手动激活（PowerShell 执行策略问题见下）：

```powershell
.\venv\Scripts\Activate.ps1
```

> ⚠️ 如果报错"禁止运行脚本"，先执行一次（当前用户级别放行）：
>
> ```powershell
> Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
> ```

## 2.5 数据库连接与 ORM 模型（database.py + models.py）

`app/database.py`：

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, declarative_base
from app.config import settings

engine = create_engine(settings.database_url, echo=False)
SessionLocal = sessionmaker(bind=engine, autoflush=False, autocommit=False)
Base = declarative_base()

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

`app/models.py`（对应技术方案里的表结构）：

```python
from sqlalchemy import Column, Integer, String, Text, DateTime, JSON
from sqlalchemy.sql import func
from app.database import Base

class CodeFile(Base):
    __tablename__ = "code_file"
    id = Column(Integer, primary_key=True, index=True)
    repo_name = Column(String(255), index=True)
    file_path = Column(String(512))
    language = Column(String(50))
    created_at = Column(DateTime, server_default=func.now())

class Chunk(Base):
    __tablename__ = "chunk"
    id = Column(Integer, primary_key=True, index=True)
    file_id = Column(Integer, index=True)
    chunk_type = Column(String(50))          # class / method / function / doc ...
    name = Column(String(255))               # 类名/函数名
    content = Column(Text)                   # 切片原文
    start_line = Column(Integer)
    end_line = Column(Integer)
    strategy = Column(String(20))            # ast / fixed
    indexed_at = Column(DateTime, server_default=func.now())  # 入库时间（供前端展示）

class Session(Base):
    __tablename__ = "session"
    id = Column(Integer, primary_key=True, index=True)
    created_at = Column(DateTime, server_default=func.now())

class Message(Base):
    __tablename__ = "message"
    id = Column(Integer, primary_key=True, index=True)
    session_id = Column(Integer, index=True)
    role = Column(String(20))                # user / assistant
    content = Column(Text)
    cited_chunks = Column(JSON)              # 引用的 chunk id 列表
    created_at = Column(DateTime, server_default=func.now())
```

## 第 1 期：索引构建管线（离线建库）

**目标**：把 Gson 源码从"代码文件"变成"可检索的切片向量"，落地到 Chroma 和 PostgreSQL。

### 详细工作

1. **克隆仓库**：`cloner.py` 完成 `git clone`，记录版本号（保证可复现）。
2. **遍历源码文件**：递归找出 `.java` 文件（可先用 `pathlib` 遍历）。
3. **AST 切分**（`chunker.py`，本期的核心）：
   - 用 `tree_sitter` + `tree_sitter_java` 解析每个 `.java` 文件；
   - 提取 `class` / `interface` / `enum` / `method` / `constructor` 等语法节点；
   - 每个节点切成一个 chunk，记录 `chunk_type`、`name`（类名/方法名）、`start_line`、`end_line`、`content`、`strategy="ast"`；
   - 同时实现一个 `strategy="fixed"` 的固定字数切分版本（供后续对比实验用）。
4. **元信息注入**：切片时把"所属类名 + 方法签名"拼进 chunk 内容前缀，提升检索语义（如 `[class JsonAdapter] public T fromJson(...)`）。
5. **向量化**（`embedder.py`）：用 `sentence-transformers` 加载 `bge-small-zh-v1.5`，对每个 chunk 生成向量。
6. **入库**：
   - 向量 + 元数据（file_path、行号、strategy）写入 Chroma；
   - 切片的元信息（不含向量）写入 PostgreSQL 的 `code_file` 和 `chunk` 表。

### 产出效果

- 一个可重复执行的建库脚本：`python scripts/build_index.py`；
- Gson 仓库被切分成数千个结构化切片，可被检索；
- 数据库中能看到完整切片元数据（供前端"切分浏览"功能使用）。

### 验收标准

- 运行脚本无报错，PG 的 `chunk` 表有数据、Chroma 有对应向量；
- 能打印出某几个切片的内容和行号，肉眼确认"切分边界正确"（类/方法完整，没被切断）。

## 第 2 期：检索链路

**目标**：给定一个自然语言问题，能从向量库中找出最相关的代码切片。

### 详细工作

1. **向量检索**（`vector_search.py`）：
   - 把用户问题用同一个 Embedding 模型转成向量；
   - 在 Chroma 中做 top-K 相似度检索，返回候选切片。
2. **关键词/混合检索**：
   - 用 PostgreSQL 的 `pg_trgm` 或简单 LIKE 做关键词召回，与向量结果融合（加权/合并去重）。
3. **重排**（`rerank.py`）：
   - 基础版：用交叉编码器（cross-encoder）或规则打分，对候选重新排序；
   - 也可用 LLM 做轻量重排（进阶）。
4. **封装统一接口**：`search(question, top_k) -> List[Chunk]`。

### 产出效果

- 一个独立的检索服务，输入问题、输出排序好的相关切片列表；
- 能够明显看出"AST 切分"比"固定切分"检索到的切片更完整、更相关。

### 验收标准

- 对固定的一组测试问题，人工检查 top-5 切片是否相关；
- 记录每次检索耗时（为后续论文"检索性能"留数据）。

---

## 第 3 期：生成链路（RAG 完整闭环）

**目标**：打通"问题 → 检索 → 拼 prompt → 调 LLM → 带引用回答"的完整问答。

### 详细工作

1. **Prompt 组装**（`llm.py`）：
   - 设计模板：系统提示词 + 检索到的切片（带编号）+ 用户问题；
   - 要求模型"仅根据提供的代码片段回答，并标注引用的片段编号"。
2. **调用 LLM API**：用 `httpx` 调 DeepSeek/通义/GLM 的 chat 接口，返回答案。
3. **引用溯源**：从模型回答中解析引用的片段编号，映射回 `chunk` 表，返回 file_path + 行号。
4. **防幻觉**：在 prompt 中强调"如果资料中没有相关信息，请明确说明"，降低瞎编。
5. **写问答接口**（`routers/query.py`）：`POST /api/query` 接收问题，返回答案 + 引用列表。

### 产出效果

- 系统第一次实现"端到端问答"：问一个关于 Gson 的问题，能得到"基于源码"的、带引用出处的回答；
- 这就是 RAG 的最小可用产品（MVP）。

### 验收标准

- 前端或 Swagger 里提问，能返回答案且能看到引用的源码片段；
- 与"直接问 LLM（不带检索）"对比，答案更准确、更可溯源。

---

## 第 4 期：会话与上下文管理

**目标**：支持多轮对话，并解决长对话上下文膨胀问题。

### 详细工作

1. **会话存储**：用 `session` / `message` 表保存每轮对话。
2. **多轮查询改写**：把"那它是怎么实现的？"这类指代问题，结合历史改写为完整问题后再检索。
3. **历史摘要压缩**：当历史超过阈值时，用 LLM 把前文压缩成一小段摘要，替换原始历史（解决"爆满"问题）。
4. **滑动窗口**：只保留最近 N 轮完整历史，更早的只保留摘要。

### 产出效果

- 系统能连贯回答"追问式"问题；
- 长对话下上下文不会无限膨胀，响应稳定。

### 验收标准

- 连续问 3-5 轮关联问题，模型能正确理解上下文；
- 观察发送给 LLM 的 token 数，确认被摘要/截断机制控制住。

---

## 第 5 期：评估实验

**目标**：用数据证明"语法感知切分 + 混合检索"确实优于基线。

### 详细工作

1. **自建测试集**：围绕 Gson 源码，编写 30-50 个中文问题 + 标准答案（或标准相关切片）。
2. **三条基线**（用同一测试集、同一 LLM、同一指标，分别独立运行）：
   - 基线 A：纯 LLM（不带检索）；
   - 基线 B：固定切分 + 向量检索 + LLM；
   - 方案 C：AST 切分 + 混合检索 + 重排 + LLM。
3. **消融实验**：固定其他变量，只改"切分策略"（ast vs fixed），单独看这个变量的贡献。
4. **指标计算**：答案正确率、引用准确率、检索命中率（recall@k）、响应耗时。
5. **记录与绘图**：用表格 + 图表汇总结果，作为论文"实验"章节素材。

### 产出效果

- 一份完整、可复现的实验数据（对比表 + 消融表 + 图表）；
- 论文"方法 + 实验"两章的核心材料。

### 验收标准

- 方案 C 在核心指标上优于基线 A、B；
- 消融实验能单独说明"AST 切分"带来的提升。

---

## 第 6 期：部署上线

**目标**：把系统部署到云服务器，形成可演示的完整产品。

### 详细工作

1. **前端联调**：Vue3 问答界面 + 切分浏览页面，接上后端 API。
2. **本地构建索引 → 迁移**：在本地跑完建库，把 Chroma 向量库目录 + PG 数据导出，上传到服务器。
3. **服务器部署**：
   - 用 `requirements.txt` 在服务器安装依赖；
   - Nginx 托管前端静态文件 + 反向代理后端；
   - 用 `uvicorn`（配 systemd 或 PM2）常驻运行后端；
   - 部署 PostgreSQL，并做内存调参（2 核 2G 需设小 shared_buffers、开 swap）。
4. **联调测试**：在服务器上跑通完整问答。

### 产出效果

- 一个可公网访问、可现场演示的完整系统；
- 答辩时可直接演示"问 Gson 问题 → 得到带源码引用的答案"。

### 验收标准

- 公网域名/IP 能正常问答；
- 服务器在 2 核 2G 下运行稳定、不 OOM。
